# control plane M1.5 — enroll、每设备 token、吊销

> 状态：实现中。上位：[`docs/design.md`](../design.md) §6.1、§7。
> 前置：M1（已合并）。**本阶段是 M4 把 hub 放上公网的前置条件。**

## 1. 要解决的问题

M1 用**一个全队共用、无法单台吊销**的预共享 token。一台机器泄露 = 全队沦陷，
且没有任何手段把某一台踢出去。design §7 明确要求这条在上公网前消失。

## 2. 范围

**做**：一次性 enroll code（TTL + 单次使用）、每设备 token、设备注册表、单台吊销、`devices`/`revoke` 命令、
第二条模块边界测试（`worker/` + `providers/` 不得 import `control/`）。

**不做**：主机身份密钥 / 指纹 pin —— 明文 HTTP 下的「指纹」需要 hub 持有密钥并证明持有，
本阶段不引入；**主机认证留到 M4 上 TLS 时由证书解决**。在那之前，节点无法验证 hub 的真伪，
这一点必须在 §7 如实记下，不能当成已解决。

## 3. 破坏性变更：共享 token 直接删除

`cc-fleet join <url> <token>` → `cc-fleet join <url> <code>`。旧的 `fleet.json` 共享 token 不再被读取。

不做兼容期。理由：npm 上什么都没发布过，没有存量用户；而保留一条"全队共用凭证"的代码路径，
等于把 M1.5 想消灭的东西留在原地，还多一个分支要守。

## 4. 握手

```
主机  cc-fleet hub                     → 打印 enroll code，例如  K7QP-3M2X
      （code 仅存在于内存：hub 重启即失效，这是特性不是缺陷）

从机  cc-fleet join http://hub:7892 K7QP-3M2X
      POST /control/enroll  { code, hostname, os, agentVersion }
      ← 201 { deviceId, deviceToken }
      ← 401 { error: "invalid or expired code" }        （码错 / 过期 / 已用过 —— 同一句话）
      ← 429 { error: "too many attempts" }              （见 §5）

从机  凭 deviceToken 连 /control/events 与 /control/msg（Bearer）
```

**失败原因一律合并成同一句 `invalid or expired code`。** 区分"错了"和"过期了"会告诉攻击者
他猜的码是否曾经存在，把一次盲猜变成一次预言机查询。

### code 的形状

`XXXX-XXXX`，取自去掉易混字符的 32 字母表（无 `0/O/1/I/L`），即 40 bit 熵。
5 分钟 TTL、**单次使用**、消费是原子的（先标记已用再返回，两台机器同时抢同一个码只有一台成功）。

40 bit 单靠熵不足以扛住高速爆破，所以熵不是唯一防线 —— 见 §5。

## 5. 爆破防护

一个 5 分钟窗口的短码，如果允许无限次尝试，就是可枚举的。

**防线只有一条：按来源 IP 限流。** 10 次失败后拒绝该 IP 60 秒（返回 429）。计数器在内存，
随 hub 重启清零 —— 与 code 同生命周期。

算一下就知道够了：码空间 31⁸ ≈ 8.5×10¹¹（约 40 bit），每 IP 每分钟 10 次，5 分钟窗口 ——
攻击者需要约 10¹⁰ 量级的独立 IP 才有像样的命中率。

> **一处设计修正。** 初稿还写了「同一 code 累计 5 次失败即作废全部 live code」。已删除：
> 它没有换来熵和限流尚未提供的任何东西，却白送了一个 DoS —— 任何人发 5 个错码，
> 就能让整个车队**永远无法接入新机器**。**一条失败模式是「谁都进不来」的防线，
> 比它所防的攻击更糟。** 保留的是失败计数器本身（`failedAttempts()`），用于**告知**
> 操作者有人在猜——这才是那条规则真正想要的部分。

## 6. 数据

`~/.cc-fleet/devices.json`，0600，**原子写**（写临时文件再 rename，避免半截文件毁掉整个注册表）：

```jsonc
{
  "devices": [
    {
      "deviceId": "laptop-home",
      "tokenHash": "sha256:…",          // 只存哈希
      "hostname": "laptop-home",
      "os": "win32",
      "agentVersion": "0.1.0",
      "enrolledAt": 1787040000000,
      "lastSeenAt": 1787041234567,
      "revokedAt": null
    }
  ]
}
```

**token 只存哈希。** 注册表泄露不等于凭证泄露 —— 节点持有明文，主机只存 SHA-256，比对时哈希后
用常数时间比较。这是 M1 那份明文共享 token 最该改掉的地方之一。

**不用 SQLite。** `control/` 不得 import `supervisor/`，而设备数量是个位数到几十，
为此把 better-sqlite3 拉进 `control/` 的依赖面不值得。

### deviceId 的取值

**= 从机上报的 hostname**，若已被另一台占用则加后缀（`laptop-home-2`）。

不用随机 UUID：profile 的 `assignments` 现阶段是**手写的**，键必须是人能认出来的名字。
一个 `a3f9c1…` 的 id 会让手写 profile 变成不可能。

**吊销是标记而非删除**（`revokedAt`），保留审计痕迹；同一台机器重新 enroll 会拿到新记录。

## 7. 明确未解决的风险

| 风险 | 状态 |
|---|---|
| 节点无法验证 hub 真伪（隧道 URL 被顶替） | **未解决**，留给 M4 的 TLS。在此之前 hub 只应跑在可信网络 |
| 明文 HTTP 上 token 可被中间人读取 | **未解决**，同上 |
| 主机被攻破 = 全部从机沦陷 | 接受（同一人所有机器），但现在至少可以逐台吊销 |

前两条在 M4 之前不得把 hub 暴露到公网。这不是建议，是 §2 的前置条件反过来说一遍。

## 8. CLI

| 命令 | 变化 |
|---|---|
| `cc-fleet hub` | 打印 enroll code 而非共享 token；code 过期后可用 `enroll-code` 再生成 |
| `cc-fleet enroll-code` | 生成一个新 code（hub 运行中） |
| `cc-fleet join <url> <code>` | 用 code 换取每设备 token 并落盘 |
| `cc-fleet devices` | 列出设备：id、hostname、最后在线、状态 |
| `cc-fleet revoke <deviceId>` | 吊销一台；其 token 立即失效（鉴权逐请求读盘） |

## 9. 第二条边界

`tests/control/boundary.test.ts` 已守住 `control/` 不向外依赖。本阶段补上反方向：

**`src/worker/**` 和 `src/providers/**` 不得 import `control/`。**

这是 design v2 §2「copilot-reverse 收缩为一个组件」的机械化保证 —— 组件不该知道控制面存在。

## 10. 测试

**单测**
- code：格式、字母表无易混字符、TTL 过期、单次使用、并发只有一个赢家、hub 重启后失效
- 爆破：同 IP 10 次失败 → 429；同一 code 5 次失败 → 作废；计数器隔离（A 的失败不影响 B）
- 注册表：enroll 落盘、只存哈希、原子写（半截文件不破坏既有记录）、deviceId 去重加后缀、
  吊销后 token 失效、吊销保留记录、重新 enroll 得到新记录
- 鉴权：正确 token 通过、错误/被吊销/未知 token 401、无 Authorization 401、常数时间比较
- 边界：两条都绿

**E2E（真实 HTTP）**
- 完整握手：起 hub → 生成 code → join → 拿到 token → 收到 desired state → skill 落盘
- 同一个 code 第二台机器 join → 401
- 过期 code → 401
- 吊销后：正在连的设备被断开，且重连 401
- 两台设备各自的 token 互不通用
- 错误信息不泄露 code 是否曾经存在

**changeset**：`minor`（CLI 破坏性变更，但版本仍在 0.x）。

## 11. 实现中发现的、比 enroll 本身更严重的 bug

手跑 CLI 时发现：**节点被吊销后静默退出，退出码 0**。

根因不在吊销，在重连退避的 `setTimeout(...).unref()`。定时器被 unref，SSE socket 一断事件循环就空了，
**进程在退避期间直接死掉**。也就是说 **hub 只要重启一次，全队节点进程都会悄无声息地退出** ——
重连逻辑存在的全部意义被它自己抹掉。

**单元测试结构上抓不到这个**：vitest 自己撑着事件循环，进程永远不会退。
所以补了 `e2e/control-node-lifetime.e2e.test.ts`，在**真实子进程**里跑 agent：

- hub 关掉后节点仍存活，且 hub 回来后重连
- 凭证被吊销 → 明确报错 + **非零退出码**（静默 + 0 是最糟的结局：用户看不到原因，
  外层 supervisor 还以为"正常结束"）
- 从未签发的凭证 → 立刻放弃，不无限重试

顺带修掉第二个：`process.exit()` 会和未完成的 fetch 抢跑，在 Windows 上把进程打成
abort（`0xC0000409`）。改用 `close()` + `process.exitCode`，让它干净收尾。
